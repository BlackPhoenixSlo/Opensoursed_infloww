# S4S media is read from its own Creator's vault at post time and uploaded by the poster's

Phase 3 left media off S4S posts because "vault media ids belong to one OnlyFans account, and no known body moves media between accounts" (docs/spec/phase-03-share-for-share.md, Out of Scope, story 8). Infloww carries up to 5 vault items on an S4S post, so this ADR changes that rule for S4S only, with no other change to ADR-0011. We decided that the media's bytes cross accounts, never its ids and never a session, and that no copy is kept on our server. When an owner sets a post's media (`PUT /admin/s4s/profiles/{account_id}/posts/{post_id}/media`), the Relay reads each vault item with the owning Creator's own OnlyFans session (`vault_media_by_id`, which also shows the item is in that vault and can be shared) and stores only its vault id and kind (`s4s_media`). At send, a request stores the media on each side's Primary post, as it already stores captions. At slot time `s4s_post` reads each of the partner's items from the partner's vault with the partner's own session into a temporary directory, uploads it to the poster's own account with the poster's own session (`upload_media`, one `of_write_paced` write each), removes the directory, and posts the returned `send_with` entries through Auto Post. Each OnlyFans call still uses the session of the Creator it acts for. It is hard to reverse because a posted copy stays in the poster's vault: removing the post does not remove the media.

What a partner sees. Before Accept, either party to a request may view a still of each item in both snapshots (`GET /admin/s4s/media/{id}`), read live from the owning Creator's vault with that Creator's session and never cached, as both already see both captions. This is the second cross-agency read after Discovery, and it is scoped to requests the caller's Creator is a party to. Discovery itself also shows a still of each item on a listed Creator's Primary post, to any Agency it is listed to, so a partner sees the post before sending a request (Infloww's request pop-up shows it); the still stops once the Creator is hidden, opted out or blocked, or the item leaves the Primary post. The schedule also reads the paired slot's tamper reason (`partner_issue`) for the same pair.

Bounds. A post carries at most 5 items. Only photos, GIFs and non-DRM videos are accepted. Reads come only from OnlyFans media hosts (no userinfo, port or backslash in the URL), with no redirects. A partner may preview a snapshot only while its request is pending or accepted. If an item has left the partner's vault (or became unshareable) by slot time, the slot ends `failed` / `media_missing` and nothing is posted; another read failure ends it `media_fetch_failed`. A row is deleted once no post, open request or unfinished slot names it, after every save, post delete and `s4s_post` run.

ASSUMPTION: the upload's claim is posted directly and not first materialized into a vault id (`materialize_to_vault`). Rung 3: the OF mirror's composer posts `send_with` the same way. Overturned if OnlyFans refuses a claim on a post.

## Considered Options

- **Keep media off S4S (Phase 3).** Rejected: Infloww's S4S posts carry media, and a text-only promo is weaker.
- **Post the partner's vault ids from the poster's account.** Rejected: OnlyFans scopes vault ids to one account, so the post would fail or attach the wrong items.
- **Copy the files to the Relay's disk at save time.** Used first, then dropped by the owner: it needs a persistent volume, disk caps and a sweep, for files OnlyFans already keeps. Its one gain, a post that survives the item leaving the vault, is not needed; that slot now fails `media_missing` instead.
- **Materialize the upload into the poster's vault first.** Rejected for now: it needs a carrier post plus a sweep, and posting the claim already files the media in the poster's vault.
