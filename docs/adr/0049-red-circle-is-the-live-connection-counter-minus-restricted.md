# The Red circle is the Live connection's unread counter minus the chats one exclusion predicate removes, not a count from our rows

**Status: proposed** (2026-11-22, `docs/spec/creator-badges/goal.txt` Phase B, D1, D2, D4–D8 in `.scratch/creator-badges/evidence/fable-r3-final.md`; owner constraints binding; nothing built yet).

A Creator tab's unread count is folded today from the first 25 chats of the Relay's held window (`service/accounts_admin_api.py` `_roster_counts_from_rows`), so a read on onlyfans.com, Infloww or another chatter's screen reaches it only at the next re-read, and a full window reads "N+". OnlyFans already pushes the answer: each Creator's Live connection sends an Unread counter frame `{"chat_messages":N}` once per read-state change from any source, under 1 s (measured: API read 0.23 s, onlyfans.com click 0.83 s, Creator send 0.85 s), counting unread unmuted chats that are sendable or whose `canNotSendReason` is `only_friends` (measured: counter 11 = 7 + 4 `only_friends`, exact), Restricted chats included; the Relay drops it today in the transcoder's "other" lane. We decided the Red circle is that counter, fed into `unread_total.observe` beside `/users/me` (`service/unread_total.py:77`), minus R, floored at 0. R is the unread chats in the latest Unread list that OF's counter counts (`of_counts`) and that the one predicate `excluded_from_badges` removes: the Fan is in our `of_restricted` registry or the row's `canSendMessage` is false, `only_friends` included (owner amendment #3; worked example: counter 11 with 4 `only_friends` → red 7). The raw counter is an input only and is never displayed anywhere (owner 2026-11-22). The owner's later "excluded unless replyable in our app" changes that one function. This settles ADR-0043's open Q1 in favour of the counter. The Relay computes; tabs only display, through the Shared refresher's snapshot (`creator_refreshed`, existing boot and seq) and a per-Creator Badge version in the Event stream ping; the `roster-counts` route keeps its path and fields, filled from this truth. Why: it moves at 0 OF calls for every Creator, in every tab at once, from every source, which no read cadence matches at ≤50 Creators. The cost: the counter does not know the house rule on Restricted chats, so the Red circle depends on R, which goes stale on restrict or unrestrict (no frame) until the next Attribution read or hover; a silently lost frame on a live socket is caught only by the refresher's `/users/me` cycle and by hover; and until Phase C, R comes from rows in the held window that the predicate excludes.

## Considered Options

- **Fold our own rows (today's Roster count).** Rejected: a 25-chat window that ages until re-read and misses reads made elsewhere.
- **Poll the Unread list or `/users/me` each Cycle.** Rejected: costs OF calls per Creator per Cycle for what the Live connection brings free, and is 120 s late under a View lease.
- **Follow the counter raw, Restricted included.** Rejected: brings back phantom red for any Creator with an unread Restricted chat, against the existing exclusion in `accounts_admin_api.py`.
