# Smart Messages' trigger list holds only per-fan triggers; mass messages sit in the bundle's Mass Messages tab on Smart Messages (the plan's follow-the-bundle exception), with a My Automations tab as the fallback if the owner vetoes

Status: accepted (owner, 2026-10-17). Amended 2026-10-17 (infloww-parity-round-2 plan review): the bundle placement was observed, so the owner's exception applies. The owner may veto the placement, and then the fallback below applies. The file name keeps its original slug so that existing links still resolve. Amended 2026-10-21 (cleanup Phase 9a, Q6): Mass Nudge (`mass_nudge`, `MassNudgeTab`, `/admin/mass-nudge/*`) is removed, by the owner's decision of 2026-10-20. The Mass Messages tab no longer mounts it. The text below that places Mass Nudge in that tab, and the second ASSUMPTION's Mass Nudge half, are kept as history only. `online_blast` (the scale broadcast) and the per-fan Nudge message (`nudge_online`) stay.

Today `/growth/smart-messages` (`app/components/growth/SmartMessagesPage.tsx`) has two tabs, "Mass messages" and "Scheduled", plus the mass composers "New Message" and "Message online fans". The page's own comment says Infloww's trigger half "is not built". We decided that a Smart Message is a triggered, one-to-one message sent to one Fan when that Fan does something: the Nudge message, the Message on purchase, and any other per-fan Trigger the Dashboard bundle shows. A Mass message is never a Smart Message, and Smart Messages' trigger list (the bundle's "Automated Messages" tab) never shows one. The reason is that one name had been covering two different concepts, one-Fan triggers and many-Fan sends, and the owner chose to keep them apart.

The owner's placement line has an exception: if the bundle puts automated mass messages somewhere else, follow the bundle and record where it was found (plan, `docs/plans/infloww-parity-round-2.md` line 10). The bundle does put them somewhere else. Infloww's Smart Messages page has two parent tabs, "Automated Messages" and "Mass Messages" (`index.9f50f370.js` `var MessageSendTitle` @14654355; the strings @14654443 and @14654486), and the Mass Messages tab has child tabs by send type, Priority mass message and OF mass message (`changeSendType({parentTab:MessageSendType.Mass` @15747892; `var massMsgList` @14707943). One "Create message" pop-up (@14716722) offers both the Mass messages and the Automated messages sections. So mass messages sit in the Mass Messages tab of Smart Messages: the mass history and bulk unsend (`MassMessagesTab`), `ScheduledTab`, the mass composers and Mass Nudge, which goes there because it is a broadcast even though its name says nudge. The Auto delete (`AutoUnsendPanel`, the "Auto-unsend mass" `unsend_messages` rule, and the composer's per-broadcast Auto-unsend) sits next to the mass list.

The bundle's Auto-unsend is per message, set in the Smart Message editor (`function Unsend$1` @14979383, "Auto unsend settings" @14981410), and only for Priority mass and Automated messages: OF mass messages do not support it (`function hasAutoUnSend` @14776278; @14793004). The original text of this ADR said a grep found no auto-delete string; that search used the wrong words. Our per-Creator hourly sweep has no Infloww counterpart, and our sends are OF mass messages, so both of our Auto deletes are ours and carry the "Inflowwww extra" label.

The move reuses existing code and leaves the Relay unchanged: there is no new sending path, and a Trigger with no existing send behind it is Not wired. Under the bundle placement no route, nav item or page-map entry is added, so no saved permission changes.

Fallback, if the owner vetoes the bundle placement: mass messages get their own My Automations tab, "Auto mass messages", alongside Auto Post and Auto Story, carrying the "Inflowwww extra" label. Smart Messages keeps its mass prefixes in the page map, so no saved role loses access. The fallback is hard to reverse, because Permission roles are keyed by nav href (ADR-0007): an Agency's saved permissions attach to the new route, which is also in the page map in `service/permissions.py` and `service/tests/test_role_enforcement.py`, so moving the tab again would orphan them. My Automations is hidden from chatter sessions, so under the fallback chatters lose the mass UI they have on Smart Messages today. The owner decides that in the same veto.

ASSUMPTION: the Layout capture `growth-smart-messages.md` records the same Mass Messages tab this amendment observed. This reading is rung 1 (the offsets above) plus rung 2 (the owner's exception names the bundle as the override). It is overturned if the capture places mass messages elsewhere, or if the owner vetoes the bundle placement and wants My Automations regardless.

ASSUMPTION: ADR-0003's amendment, which keeps `nudge_online` and `mass_nudge` behind the Legacy flag, governs Messages Pro extras and the flag-only `/automations` page. It does not govern these Growth pages (and the fallback's My Automations tab), which the Nudge message and Mass Nudge now reach with the flag off. The rung is 3, because neither group is `legacy` in `app/lib/nav.ts`. Mass Nudge stays hidden from chatter-only sessions, which never see it today. This is overturned if the owner wants both of them flag-only.

## Considered Options

- **Keep today's Smart Messages page, with the mass list as its first view.** Rejected by the owner, because it hides the trigger half under a mass list. The bundle layout differs from this option: Automated Messages is its own parent tab, the default, and the trigger list never shows a mass message.
- **A My Automations tab for mass messages.** This was the owner's default. It is now the fallback, because the bundle places mass messages on Smart Messages and the owner's exception says to follow the bundle.
- **A new Growth page for mass messages.** Rejected. Neither Infloww nor our nav has one.
