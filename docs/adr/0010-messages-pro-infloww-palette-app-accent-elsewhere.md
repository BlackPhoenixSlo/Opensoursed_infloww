# Messages Pro takes Infloww's palette by default; the App accent stays everywhere else

ADR-0001 gave Messages Pro Infloww's Geometry and Inflowwww's colours. The look-and-feel plan (`docs/plans/messages-pro-look-and-feel.md`, "Decisions already made") reverses the colour half for Messages Pro only: the Infloww palette (blue accent, grey bubbles, near-black shell, and Infloww's divider and text colours) becomes Messages Pro's default, and the purple App accent (`--color-accent`, `app/app/globals.css:30`, `:132`) stays the theme accent on every other screen. The Geometry half of ADR-0001 stands. The values are written in Messages Pro's JSX, mapped one by one in the Colour inventory; since Phase 1 they sit in the inline style of one Messages Pro component, `InflowwPalette` (`app/components/chat/InflowwPalette.tsx`), which re-declares the `--color-*` variables on Messages Pro's subtree, plus one `--inf-*` variable there wherever the inventory gives one class a second value, which that element reads with the app token as its fallback; they never enter the Geometry token module (the colour check in `app/lib/messagesPro.test.ts:283-289` keeps guarding it), and the shared `--color-*` tokens are not changed, because changing them would recolour the whole app and drop the App accent with it. The reason is the plan's goal: someone who knows Infloww's Messages Pro should open ours and see Infloww, and with the layout already matched (parent effort, `docs/messages-pro-parity.md`) colour was the largest visible difference left. The cost is that Messages Pro, Settings (ADR-0009) and the rest of the app now carry three colour sources, and going back means redoing every row of the Colour inventory.

ASSUMPTION: Messages Pro does not read the `--if-*` Infloww tokens, because ADR-0009 keeps them to the Settings components and says reading them elsewhere re-opens ADR-0001; the plan's "JSX only, per ADR 0001" is read as "in the components, not in a token module" (rung 3). Overturned if the Phase 1 spec shows one shared block of Infloww colour variables is smaller than per-component values, in which case ADR-0009's scope gets amended.
ASSUMPTION: the "near-black shell" is Infloww's dark palette; what Messages Pro shows under `html[data-theme="light"]` is left to the Phase 1 spec, which must state it and flag it. Overturned if the human wants Messages Pro to stay dark whatever the app theme is. UPDATE 2026-10-18: the owner asked for Infloww's light colours in Messages Pro too, so under the light app theme `InflowwPalette` now lays Infloww's light set over the dark one (`docs/infloww-sidebar-palette.md` §3).
ASSUMPTION: ADR-0001's inferred reason for keeping our colours (distance from Infloww's visual identity, `docs/parody-voice.md`) is now carried only by "no Infloww logo or screenshots"; overturned if the human treats colour as part of that distance.

## Considered Options

- **Keep ADR-0001's app colours in Messages Pro.** Rejected by the plan's binding colour decision.
- **Switch the shared tokens to Infloww's values.** Rejected: the purple App accent must stay outside Messages Pro.
- **Put the colours in the Geometry token module.** Rejected: the plan and ADR-0001 keep colour out of it, and its colour check is an Acceptance line.
