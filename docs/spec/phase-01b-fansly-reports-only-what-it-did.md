# Phase 1b — Fansly reports only what it did

**Objective.** Every Fansly Shim method an OnlyFans caller in `service/` reaches is built, Unsupported or Blocked, every caller of an Unsupported or Blocked one stops at a Side-effect gate before it sends, claims or writes, Fansly banks only chat PPV (code 2007), and a Capability test in `scripts/run-tests.sh` holds every registered Backend module's Shim to that.

## Problem Statement
A Fansly Creator's chatter or owner is told things happened that did not. Restrict sends a `.` DM and marks the chat read before the Shim (which has no `restrict_user`) fails. Vault remove marks media removed after the Shim answered `success:false`. A mass send opens a run and reports the Shim's skip as sent. A chat search that never ran shows "0 matches". Expiry lifecycle burns a claim and can send a message promising a discount Fansly cannot give. Eight automation calls (`add_users_to_lists`, `list_users_in`, `rename_list`, `delete_list`, `mass_message_history`, `message_templates`, `my_settings`, `set_subscription_discount`) AttributeError mid-run (measured: `fansly/test_fansly_capability.py` exits 1 today). On money, codes 2008 and 32007 bank from generic `price`/`amount` keys never observed, and a chat message's `totalTipAmount` is banked raw as a dollar tip with no provider id. The guard that should catch all this scans `server.py` routes only, does not fail on route misses (108 in `server.py`; 154 across `service/` under this spec's scan, 140 of them outside the verdict table below, measured read-only 2026-11-24), and is not in the test runner. Two shape tests need a HAR that is gitignored and absent.

## Solution
Fansly does what it can and refuses the rest out loud. List-add works on Fansly. Every other gap is marked: an Unsupported method raises or returns nothing that reads as success; a Blocked method raises a typed error until a Capture session records it. The Relay routes and automations that reach them answer 501 or skip before any DM, claim, run row, skip-list row or local mirror write. The revenue lane banks only what a Proof purchase showed (2007 from `accountMediaPrice`), tips stop being banked from chat messages, and each tick logs how many unbanked money codes it actually saw. The Capability test loops every Platform registry entry with a Backend module, scans all of `service/`, fails on any route miss and on any other miss not on a frozen, shrink-only Unreached list, and runs with the other offline Fansly tests from `scripts/run-tests.sh` on checked-in scrubbed fixtures. OnlyFans behaviour does not change.

## Implementation Decisions
- **Owns.** `fansly_shim` (markers, the route-miss marker table, list-add, `resubscribe_user` marker, money sets, tip mapping, purchase feed); a new `side_effect_gate` module in `service/`; in `server`: `_platform_write` and the routes for restrict, unrestrict, block, unblock, search users, search chat, chat media (two), scheduled messages, list members, rename list, delete list, delete chat (`of_delete_chat`, `server.py:5722-5731`, which Bulk Delete calls once per chat), mass history (the Stats group feed, `GET /admin/mass-messages`, `POST /admin/mass-messages/refresh`), subscription discount; `mass_queue_api.of_send_or_schedule_mass`; `vault_ai_api.hide_item`; `vault_of_folders.hide_duplicates`; automations `send_mass_message`, `mass_premade`, `unsend_messages`, `lifecycle_messages`, `smart_list_sync`; `fansly_revenue`; `scripts/run-tests.sh`; the Fansly tests and fixtures; `fansly/FANSLY_PARITY_STATUS.md`, `fansly/capture/CAPTURE_TODO.md`. Not owned: the `Shim` export and the API-error handler's `status_code` read (Phase 1a's; this Phase only raises through them).
- **Markers.** `fansly_unsupported(reason)` and `fansly_blocked(reason)` keep their attribute markers. Given `returns=`, they return it as today (pin, unpin, mark unread, the vault/story stubs, `subscribers_chart`, `recent_expired_subscribers`, `like_post` are unchanged). Without `returns=`, they raise `FanslyUnsupported` / `FanslyBlocked`. Both subclass `FanslyAPIError` and carry `status_code = 501`. `resubscribe_user` drops its `returns=` and raises: its `{"success": False}` is truthy, so `auto_follow`'s `except` fallback to `follow_user` (`service/automations/auto_follow.py:631-636`) never runs and the fan is counted `refollowed` with no follow.
- **Verdicts** (ticket 04, binding; rows marked † were added by the review under ticket 04's rule "gate before side effects, never fake success"):

| Method | Verdict | Shim answer |
|---|---|---|
| `add_users_to_lists` | built | `POST /lists/commands`, one `type:1` `listItem{id,listId}` per fan; returns `{listId: [fan ids as strings]}` read from the echoed commands |
| `list_users_in`, `rename_list`, `delete_list`, `block_user`, `unblock_user`, `search_users` | Blocked | raises |
| `mass_message_history`, `engagement_messages` †, `chat_media`, `scheduled_messages`, `schedule_mass_message` | Blocked | raises (`engagement_messages` is what the Stats group and direct feeds call, `service/server.py:5333`, `service/of_stats_api.py:199`; `chat_media` and `scheduled_messages` replace today's empty envelope; the others replace an AttributeError) |
| `resubscribe_user` † | Blocked | raises (was `returns={"success": False}`) |
| `send_mass_message` | Blocked | carries the marker; without `confirm_live_broadcast` raises instead of returning a skip; the confirmed path stays for the owner's one-person broadcast capture |
| `restrict_user`, `unrestrict_user`, `search_chat`, `set_subscription_discount` | Unsupported | raises |
| `message_templates`, `my_settings` | Unsupported | `returns=None` (welcome reads "OF greeting off" and sends its own; the Fansly follow-rule mirror stays Blocked pending a paid-subscribe capture) |
| `delete_chat` ‡ | Unsupported | raises; no capture or bundle note names a Fansly chat delete (`fansly/capture/RECIPES.md`) |
| every other route miss ‡ (140 measured outside this table, `delete_chat` among them) | Unsupported, or Blocked where a capture could build it | raises; one `{name: (verdict, reason)}` table in the Shim applies the markers, so no per-method stub is written |

‡ added by the plan review (shared-ownership ruling: `delete_chat` and route-miss sizing are 1b's).

- **Side-effect gate.** `side_effect_gate.refusal(client, name) -> str | None`: the reason when `name` is missing on the client or carries either marker, else None. `client` may be a Shim instance or the Shim class: it reads `getattr(client, name, None)` and the marker attributes only, never `self` state, so Phase 1c's Drift test passes `fansly_backend.Shim` itself. No Platform key, so the registry's scan guard stays green. `server._platform_write` uses it, so it now also refuses Blocked methods. Each gated route calls it as its first client step and answers 501 `"<what>: not on this platform"`; automations return `{"status": "skipped", "reason": "platform_lacks:<name>"}`. Placement: restrict/unrestrict before the ack send, mark-read and skip row; mass route before `_reserve_send` (checks `schedule_mass_message` when scheduled or saved, else `send_mass_message`), so audience resolution and the Auto_Exclude sync are never entered; `send_mass_message` automation right after its client is built (`send_mass_message.py:332`), before the fence, `ensure_exclude_list` and any run mint; `mass_premade` keeps its client-less start and, when `send_mass_message`'s run returns a `platform_lacks:` skip, returns it without `_drip_rest`; `unsend_messages` sweep, once its client is built, drops the mass lane (no `_refresh_mass_cache`, no `_sweep_mass_targets`, no `_reapply_recent_unsends`) when `mass_message_history` is refused, and reports `mass_skipped: "platform_lacks:mass_message_history"`; lifecycle after its client is built and before the loop, dropping only the plans whose chosen message carries a discount (`messages[idx]["discount"]` for a `DISCOUNT_KINDS` kind) when `set_subscription_discount` is refused, so those fans get no lease, claim or send and plain-message plans run as today; Smart list sync before tombstones and list claims, on `list_users_in` (its crash-recovery rewrite of stale `syncing` rows to `error`, which runs before any client, stays: it is true on every platform); vault item and duplicate remove before `hide_vault_media`; delete chat before `_paced_of_write` and `_bust_chat_list_and_badges`, so a refused delete sends nothing and drops no cache; every other marked route miss relies on the typed-error handler alone, unless marking it finds a send, claim or local write before its client call, in which case that route gets a pre-check too; the Stats group feed on `engagement_messages`, `GET /admin/mass-messages` and its refresh on `mass_message_history`, before the stale-cache safety net (which today swallows the error and serves an empty cache).
- **Typed error at the route.** Phase 1a's Backend module API-error handler answers `getattr(exc, "status_code", 502)`; this Phase's 501 subclasses ride it, so a Blocked or Unsupported raise that slips past a pre-check still surfaces as 501, not 500 or a fake 200.
- **Money** (ticket 03, binding). The Shim gains a Banking set `{2007}` with price key `accountMediaPrice` alone; `_PURCHASE_NOTIF_TYPES` becomes the Unlock set (2007, 2008, 32007) and keeps `_PRICE_METADATA_KEYS` for chips and rail text only. `purchases()` returns `{"sales": [...], "unbanked_seen": {code: n}}` from one feed read, counted before any filtering and on ticks with zero sales; `sales` filters on the Banking set; `unbanked_seen` counts rows on that page per watched code (7001, 15006, 15016, 2008, 32007, 45012) plus `2007_unpriced` for a 2007 row with no usable `accountMediaPrice`. `unbanked_purchase_codes()` and the once-per-process log retire. `fansly_revenue.run_one_tick` banks `sales` as today (`ppv_message`, gross, net/fee/VAT NULL, `cleared`, keyed by notification id, USD) and logs `fansly_revenue_unbanked_seen account=… counts=…` when they change, per account. `of_message` keeps `isTip` and omits `tipAmount`. The websocket never banks; the notification poll stays the only money writer. Prospective only: rows already banked from 2008, 32007 or chat tips are not touched.
- **Capability test.** `service/tests/test_platform_capability.py`, under `_harness`. For each registry entry with a Backend module it takes that module's `Shim` class. Surface: every name referenced as an attribute of a word-bounded `client.` or of `_get_client().`, or as a string literal in `getattr`/`hasattr` on either (`unsend_messages.py:482`), in `service/**/*.py` outside `service/tests`, kept only when `OFClient` defines it (drops httpx-style `client.get` noise; measured 232 of 244 names). Each name is built, Unsupported, Blocked or missing; missing fails unless it is on the test's per-Platform Unreached list, a `{name: reason}` dict. A name reached through `_get_client().` (a Relay route) can never be Unreached: any route can be called for a Fansly Creator, so plan.md's "fails on route misses" holds literally and each such miss is marked in the Shim (Unsupported, or Blocked where a capture could build it) with a reason, which the typed-error handler answers as 501. The Unreached seed is today's non-route misses minus the verdict table, each with a reason; never grown in this Phase. It prints Blocked reasons each run. The test body moves here; `fansly/test_fansly_capability.py` stays as a thin entry point that runs it and exits with its code, so ticket 04's acceptance path still exits 0.
- **Runner.** `scripts/run-tests.sh` runs `run_tests_parallel.py` on `fansly/` too, under its own `──────── Fansly (fansly/test_*.py) ────────` header, only when no pattern is given; a failure there sets `fail=1`. `fansly/test_relay_e2e.py` (live) becomes `fansly/live_relay_e2e.py`, outside the `test_*.py` glob.
- **Fixtures.** `fansly/fixtures/` holds synthetic JSON shaped from `fansly/capture/RECIPES.md`: the write requests `test_har_replay` rebuilds (list-add among them), the inbox/thread/subscriber reads `test_shim_shapes` reshapes, and `signer_vectors.json` (path, device id, check key -> digest) computed once by running the bundle's own `cyrb53` under local `node`. The bundle is not in the repo; the one observed copy is `/private/tmp/fansly-bundle-ev/main.14d24b3e179efdb7.js` (sha256 `308fc0e7…aed56`), and the JSON records that file name, its sha256 and the exact function text run, so the vectors' source is checkable without the bundle. `test_har_replay` and `test_shim_shapes` default to the fixtures (a HAR path argument still works) and fail when any fixture operation is not rebuilt, not only when zero are. A new `fansly/test_signer_vectors.py` checks `client_check` against them.
- **Contract with Phase 1a.** Consumed, not added: the Capability test loops `platforms.backends()` and reads each module's `Shim` (1a's `fansly_backend.Shim = FanslyShimClient`); the 501 subclasses rely on 1a's `status_code` read.
- **Size and order of work.** The first slice runs `test_platform_capability.py` red on today's tree and records the real route-miss count in `FANSLY_PARITY_STATUS.md`. A read-only run of this spec's scan on 2026-11-24 found 154 route-reached names missing (140 outside the verdict table), more than one slice can mark with reasons, so the work splits into two tickets: **gates + markers** (verdict table, route-miss marker table, `side_effect_gate`, every route and automation gate, delete chat, Capability test and its `fansly/` entry point) then **money + fixtures** (Money, `fansly_revenue`, fixtures, signer vectors, shape and replay tests, the `scripts/run-tests.sh` Fansly block, `live_relay_e2e.py` rename, docs). The Capability test runs from the first ticket through the `service/tests` glob; the Fansly block waits for the fixtures because `test_har_replay` and `test_shim_shapes` fail without them.
- **Docs.** `fansly_revenue`'s module docstring and `FANSLY_PARITY_STATUS.md` say the Banking set is `{2007}`, tips and subs wait for Proof purchases, and ingestion reads the first notification page only. Each verdict above goes in the parity doc, with `cancel_scheduled` (sends every id to the post endpoint) recorded as a known hazard. The one Capture session (list members, rename, delete, block + unblock, username search, one scheduled broadcast row) and the three Proof purchases (chat PPV, paid sub not a gift code, chat tip) go in `CAPTURE_TODO.md`. ADR-0055 and ADR-0056 move to accepted.
- **Schema.** None.
- **Contracts.** New 501 bodies on the routes above for a Fansly Creator (`detail: "<what>: not on this platform"`); the Backend APIError handler's status comes from the exception. OnlyFans responses are unchanged.

## Testing Decisions
Seams, highest first. Tests drive the real route functions and automation entry points with the real `FanslyShimClient` class (no session: marked methods never touch `self`) and assert outcomes, never the gate's internals.
- **Route and automation entry points**, `service/tests/test_fansly_unsupported_writes.py` (extended): restrict answers 501, sends no message, writes no skip row, does not mark read; unrestrict 501; block, unblock, search users, search chat, both chat media routes, scheduled messages, list members, rename, delete, the Stats group feed, `GET /admin/mass-messages` (empty cache), its refresh and discount answer 501; vault item and duplicate remove answer 501 and leave `removed_at` NULL; `DELETE /api/of/v2/chats/{id}` answers 501 with no pacer slot taken and no cache bust; one sampled route per verdict kind from the route-miss marker table answers 501 with its reason; `side_effect_gate.refusal` gives the same answer on `FanslyShimClient` and on an instance for a built, an Unsupported, a Blocked and a missing name; the vault backfill answers `synced:false` and leaves `synced_at` NULL; the mass route, for immediate, scheduled and save-for-later bodies, answers 501 with no mass run, no reserved key and no audience or `ensure_exclude_list` call on the fake; the `send_mass_message` automation skips with no run and no list write; premade skips and enqueues no follow-up; auto-unsend with a seeded mass cache row makes no `cancel_scheduled` call and flips no row, while a per-chat target still runs; the expiry lifecycle with one discounted and one plain message leaves the discounted fan with no claim and no send and sends the plain one; Smart list sync, with a seeded active list and a tombstone, leaves both rows unchanged; each case repeated with an OnlyFans fake reaches the client as today.
- **Positive entry points**, same file: `POST /api/of/v2/lists/users` on the real Shim with a request recorder sends the recipe's `type:1` body and returns the echoed ids as strings; a `send_welcome` run on a Fansly fan sends the Relay's own greeting and marks the fan welcomed only after it; an `auto_follow` `refollowed` outcome calls `follow_user`.
- **Revenue lane**, `service/tests/test_fansly_revenue.py`, driving raw notification rows through the real Shim's `purchases()` into `run_one_tick`: a 2008 row with `price` and a 32007 row with `amount` bank nothing and still unlock; a 2007 row carrying only `price`/`amount` banks nothing and counts `2007_unpriced`; a priced 2007 banks one 300-cent gross row once across two ticks; a page of 7001 ×2 and 15016 ×1 with no sales logs those counts and banks nothing; the same page on two ticks logs once, a changed page logs again and an empty page after non-zero logs once; existing cases keep passing on the new `purchases()` shape.
- **Websocket pump**, `service/tests/test_fansly_ws_pump.py`: a captured frame with `totalTipAmount=3000` persists one inbound row, writes no transaction and leaves the fan's spend unchanged; an OnlyFans tip frame still banks.
- **Shim shapes**, `fansly/test_shim_shapes.py`: 2008 still marks the fan's message unlocked; `of_message` with `totalTipAmount` has `isTip` true and no `tipAmount`; `add_users_to_lists` body matches the recipe and returns string ids. `fansly/test_automation_methods.py` pins the list-add request body.
- **Contract**, `service/tests/test_platform_capability.py` as above; red first against today's tree.
- Prior art: `test_fansly_unsupported_writes.py`, `test_fansly_revenue.py`, `test_fansly_ws_pump.py`, `test_lifecycle_messages.py`, `test_smart_list_sync.py`, `test_role_enforcement.py` (reads repo files from a service test), `fansly/test_automation_methods.py` (request recorder).
