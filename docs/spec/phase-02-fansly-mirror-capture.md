# Phase 02 — Read-only Fansly Mirror capture

**Objective.** A minimal Capture gate, proven by a five-case local self-test in the owner's creator Chrome (CDP :9231), lets the coordinator run a 5-page tracer on live Fansly that writes nothing and records the Tracer facts Phases 3 and 4 are coded against; the same gate then takes the Mirror capture of every page and State ticket 01 lists into `~/Downloads/fansly-live-capture/`, with a Capture manifest built only from audited sessions.

## Problem Statement
The owner wants a Fansly Manager "like OF", and OF's look came from a static copy of the real UI. That copy can only come from the owner's own signed-in creator session, and the owner's constraint is that nothing is written to Fansly while it is taken. Fansly writes without a click: opening an unread thread acks it, the notifications page acks rows, the app announces presence and logs profile impressions, and most pages' open-time traffic was never recorded. The existing rig cannot keep that promise: `record.py` only watches (and drops redirected POSTs), `drive.py` defaults to port 9222 (an unrelated Chrome) and its synthetic `.click()` cannot open CDK menus, `start_chrome.sh` opens `https://fansly.com/` straight away, and a CDP gate that is killed mid-run fails open, leaving live Fansly tabs talking freely. Several facts the generator and the app need (Fansly's dark marker, the banner field, DOM class names, opener selectors, which telemetry writes fire) can only be learned from a live page, so they must be measured before that code is written.

## Solution
A new Capture gate attaches to every target of the creator Chrome before the first Fansly navigation and lets only GET, HEAD and OPTIONS through, on every host. A known On-open write (POST to the Fansly API at an exact path) gets a local fake reply; an AWS WAF challenge POST continues and is logged apart; every other request is failed and halts the run, blanking the tabs. Sockets are blocked and a WebSocket stub is armed on new documents as the fallback, and the tabs are reloaded after arming so no earlier socket survives. A separate watchdog blanks every web tab and leaves a durable trip marker the moment the gate's heartbeat goes stale, so a killed gate cannot leave Fansly live or pass an audit. Before any Fansly page opens, a five-case self-test in that same Chrome proves the gate against listening localhost servers whose own logs are the oracle; `run` refuses to arm without it. The coordinator then drives a 5-page tracer with `drive.py` verbs (trusted clicks, keys, waits, save), audits it, and writes the Tracer facts into RECIPES before any Phase 3 or 4 code starts. The rest of the plan is captured later into the same capture root, re-runnable per entry; `gate.py manifest` builds the Capture manifest from the saves of sessions whose Gate audit passed. Refreshing the copy after a Fansly release is the same capture and generator run again, by hand.

## User Stories
1. As the owner, I want no write of any kind reaching Fansly during a Mirror capture, so that capture changes nothing on my creator account.
2. As the owner, I want the Capture gate to decide every request of every target (pages, popups, iframes, workers, service workers) on every host, so that an unrecorded page's write or the presigned S3 upload host cannot slip past a host filter.
3. As the owner, I want GET, HEAD and OPTIONS to continue and every other method to be denied by default, so that safety does not depend on knowing every write in advance.
4. As the owner, I want a redirect hop decided at the request that caused it, so that a `POST→303` is denied at the POST.
5. As the coordinator, I want each known On-open write (`/message/ack`, `/notifications/ack`, `/status`, `/it/pis`, `/mediastory/view`) answered locally only when it is a POST to the Fansly API origin at that exact `/api/v1/` path, in the best reply shape on record and with that shape's provenance logged, so that the Fansly UI renders as if the write succeeded while nothing leaves the machine and no look-alike path on another host or method is faked.
6. As the owner, I want any other request outside GET/HEAD/OPTIONS to be failed, the run halted, every web tab blanked and every later request denied, so that a new On-open write stops the run instead of being guessed at.
7. As the coordinator, I want a third-party telemetry write (Intercom, Google Tag Manager/Analytics) to halt like any other unknown write, and to join the On-open table with a local `204` only after a halted tracer names it and RECIPES records it, so that ADR-0065's "anything else fails and halts" holds without a standing exception.
8. As the owner, I want AWS WAF challenge POSTs (POST to `*.awswaf.com` only) continued and logged as `waf`, so that the bot check does not force a re-login (owner may veto).
9. As the owner, I want every WebSocket blocked after arming, a WebSocket stub that closes at once armed on every new document as the fallback, and the open tabs reloaded, so that no socket opened before the gate survives or reconnects even if the block leaks.
10. As the owner, I want any socket handshake that completes or any socket frame sent after arming to halt the run, so that a socket leak is a hard stop, not an audit footnote.
11. As the owner, I want a new target to resume only after its Fetch interception, socket block, stub and service-worker bypass are armed, and closed with a halt if arming fails, so that no target runs a line ungated.
12. As the owner, I want a separate watchdog process that, within about 2 seconds of the gate's heartbeat going stale, blanks every http(s) page target in that Chrome and writes `WATCHDOG_TRIP` with the reason into the session, so that a killed or hung gate can neither fail open on live Fansly tabs nor leave a session that looks clean.
13. As the owner, I want the gate to halt when the watchdog's own heartbeat goes stale, so that the run never continues without its fail-safe.
14. As the coordinator, I want a `blank` command that empties every web tab of the creator Chrome, so that no Fansly page is live before the gate arms.
15. As the coordinator, I want `gate.py selftest` to run its own gate and watchdog against pages served from localhost only, so that the gate is proven in the very Chrome it will guard before the first Fansly navigation.
16. As the coordinator, I want the self-test to refuse to start while any page target is on a Fansly host, so that its kill-the-gate case never opens a fail-open window on Fansly.
17. As the coordinator, I want the self-test's local HTTP server to listen and log every request it receives, every case judged from that server log (not only from `gate.jsonl`), and exactly five cases: a GET continued; a POST from the page failed with a halt and the server receiving nothing; a POST from a dedicated worker and from a page controlled by a service worker registered before arming, both failed and the server receiving nothing; the gate killed with SIGKILL while the page posts every 100 ms, followed by the watchdog blanking the tab, writing `WATCHDOG_TRIP`, the server logging zero POSTs after the kill, and `audit` of that session failing; and a negative control (with no gate, the local POST reaches the server), so that a pass proves delivery was prevented and that the test can see a leak.
18. As the coordinator, I want the self-test to write `selftest.json` with the Chrome's browser id and one verdict per case, and exit non-zero on any failure or any missing case, so that "self-test passed" is a file, not a claim.

## Implementation Decisions
- **Owns.** `fansly/capture/gate.py` (new: the Capture gate, watchdog, self-test, audit, manifest, plan check, blank, stop); `fansly/capture/drive.py` (modified: port rule, gate guard, capture-tab pinning, mirror verbs); `fansly/capture/mirror_plan.json` (new: data from ticket 01); `fansly/capture/README.md` (new "Mirror capture" section, refresh line); `fansly/capture/RECIPES.md` (On-open write table with provenance, Tracer facts); `fansly/capture/CAPTURE_LOG.md` (coordinator's run entries); new plain-script tests `fansly/test_capture_gate.py` and `fansly/test_capture_drive.py`. `record.py` and `start_chrome.sh` unchanged.
- **Interfaces.** `gate.py` subcommands; `--root` (default `~/Downloads/fansly-live-capture`) on all; `--port` (required, 9222 refused) on those that touch Chrome (`run`, `watch`, `selftest`, `blank`, `stop`):
  - `run [--fan-account-id ID]` — check the self-test binding, arm, reload web tabs, pick the capture tab, write `ports/<port>.json` with `armed: true`, gate until `stop` or halt; prints the session id and counts only.
  - `watch` — the watchdog, a separate process.
  - `selftest` — spawns its own `run` (against the self-test's local API origin) and `watch`, plus the local logging server; writes `<root>/selftest.json`; non-zero on any failed or missing case.
  - `audit --session ID` — writes `sessions/<id>/audit.json`.
  - `manifest` — writes `<root>/manifest.json` from the root's pages, the plan and the sessions' audits.
  - `blank --port`, `stop --port`, `plan --check`.
  Pure functions the CLI wraps (the unit seam): `decide(method, url, resource_type, halted, api_origin) -> Verdict{action: continue|fulfill|fail, reason, halt: bool, body, provenance}`, `on_open_reply(method, url, api_origin) -> (body, provenance)|None`, `redact_path(path, identities) -> str`, `is_stale(beat, now, max_age)`, `selftest_binds(selftest, browser_id) -> refusal|None`, `audit(session, now) -> AuditResult`, `build_manifest(root, plan, audits) -> manifest`, `check_plan(plan, required) -> errors`, `unblanked_refusal(targets) -> refusal|None`.
  `drive.py`: `PORT` env with no default; `--root` (default `~/Downloads/fansly-live-capture`) to find the port's gate session; existing verbs keep their behaviour when no gate session is open on the port; under an open session every verb uses the recorded capture tab. New verbs `tclick <sel>`, `key <Escape|Tab|ArrowUp|ArrowDown|ArrowLeft|ArrowRight>`, `wait [--gone] <sel> [--timeout s]`, `save <id> --state <page|name> --opener <selector> --settled <sel> [--reset-key K --reset-gone <sel>]`, `assets`, `skip <id> --reason <text> --tried <selectors>`. Pure guards importable from it: `guard(port, verb, root, now) -> refusal|None`, `thread_allowed(group_id, unread_obs) -> bool`, `save_allowed(entry, tab_url, last_nav) -> refusal|None`. `drive.py` imports the gate's path and heartbeat helpers from `gate.py` (same directory) so the two never disagree.
- **Schema.** None (no database). Capture folder layout, outside the repo:
  ```
  <root>/selftest.json
  <root>/ports/<port>.json              # {session, armed, capture_target_id, browser_id}; drive.py guards every verb
  <root>/sessions/<id>/{gate.jsonl, heartbeat, watchdog.heartbeat, HALT?, WATCHDOG_TRIP?,
                        unread.jsonl, identities.json, account-me.shape.json, audit.json}
  <root>/pages/<id>.{html,meta.json,png}  <root>/static/  <root>/assets.json  <root>/skipped.json  <root>/manifest.json
  ```
  Plan entry ids are path-like (`creator/stats/overview`, `messages/thread/state-reaction-picker`); a State's file sits under its parent page's id, following OF's `<page>/state-<name>`.
- **Contracts.**
  - `gate.jsonl` line: `{ts, session, target_type, method, host, path, query_keys, resource_type, decision: continued|faked|denied|waf|halted, reason, provenance?}`; plus `{event: armed|reloaded|ws_created|ws_handshake|ws_frame_sent|halt|watchdog_stale|stopped}` lines. `path` goes through `redact_path`. No header, body, cookie, token or query value is ever written.
  - `manifest.json` (Phase 3's only input; matches Phase 3's consumed contract, extra fields ignored there): `{audit: {passed, sessions: [{id, verdict}]}, bundle_hash, theme, complete, identities: [{role: "creator"|"fan", username, displayName, accountId}], entries: [{id, kind: "page"|"state", file: "pages/<id>.html", url, final_url, state, opener, settled_selector, reset, bundle_hash, theme, session, canvases, shadow_roots, iframes, meta, png}], skipped: [{id, reason, tried}], unaudited: [id], not_in_plan: [id], assets: [{url, file: "static/<...>"}]}`. `audit.passed` is true only when every session that contributed an entry passed (by construction: unpassed sessions' saves are left out) and `complete` is true. `bundle_hash` is the entries' hash when they share one; mixed hashes are left for Phase 3 to refuse. Account ids are strings; every `file` stays inside the capture root.
  - `mirror_plan.json`: `[{id, kind, url, parent?, opener?, tracer?, optional?}]`, URL templates using `{username}`, `{groupId}`, `{albumId}`, `{listId}`, `{postId}`, `{coperformerId}`, filled at capture from the session's own data.
  - Fake On-open replies: status 200, `application/json`, matched only for POST to the API origin (`https://apiv3.fansly.com`, or the self-test's local origin) at exactly `/api/v1/message/ack`, `/api/v1/notifications/ack`, `/api/v1/status`, `/api/v1/it/pis`, `/api/v1/mediastory/view`. Bodies and provenance: `/message/ack` → `{"success":true}` (recorded, RECIPES.md); `/status` → `{"success":true,"response":{"accountId","statusId":1,"lastSeenAt","updatedAt"}}` (recorded, RECIPES.md); `/it/pis` → the shape the coordinator copies into RECIPES from the local recording before the first live session, `{"success":true}` until then (`unverified`); `/notifications/ack` and `/mediastory/view` → `{"success":true}` (`unverified`; notifications ack fires only with unread rows, BUNDLE_DERIVED.md:131-155). An `unverified` fake firing is a warning in the audit naming the page saved next, for the coordinator's screenshot check; it is never a failure, because the write never left the machine.
  - Tracer facts (RECIPES.md section, written by the coordinator, read by Phase 3 and 4 implementers): `dark_marker`, `banner_field` (name + location shape), `class_hooks` (avatar, banner, rail, message, post, bio, note, list name), `opener_forms`, `telemetry_halts` (host + path, then its fake). Names only, never values.
- **Decision order in the gate** (one place, `decide`): halted → deny all; method in GET/HEAD/OPTIONS → continue; POST to the API origin at an On-open path → fulfill fake; POST to `*.awswaf.com` → continue as `waf`; else fail and halt. Fetch pattern is every URL at request stage; response stage only for `/account/me`, `/account?ids=` and `/messaging/groups` GETs on the API origin, read for identity and unread then continued.
- **Halt.** The gate writes `HALT` with the reason, switches to deny-all, navigates every http(s) page target to `about:blank`, keeps its Fetch armed, and exits non-zero only after the watchdog sees the HALT marker. A halted session's audit always fails.
- **Watchdog trip.** On a stale gate heartbeat the watchdog blanks every http(s) page target, closes any other http(s) target, writes `WATCHDOG_TRIP` with the reason, and keeps blanking until `ports/<port>.json` is removed by `stop` or the coordinator. A tripped session's audit always fails and none of its saves reach the manifest.
- **Sockets.** A `WebSocket` that closes at once is injected on every page, iframe and worker session before it runs, always; it is the block, because `Network.setBlockedURLs` does not stop sockets on Chrome 158 (measured 2026-11-27: with the stub off, page, `blob:` worker and service-worker handshakes all reached the self-test server). The gate watches `Network.webSocketCreated/HandshakeResponseReceived/FrameSent` on every session; a socket created, a handshake response or a sent frame after arming halts and fails the audit, since the stub never creates a real socket. A second stub disables `navigator.sendBeacon`, `fetch(…, {keepalive: true})` and `fetchLater`, because Fetch never sees unload traffic (measured 2026-11-27: gate lines stayed 0 while the beacon reached the server). Both stubs are armed with `runImmediately`, so a tab opened after arming gets them on its first document. `window.open` is wrapped so the returned window gets both stubs before the page sees it (measured 2026-11-27: without it a popup's grabbed keepalive fetch left under the armed gate; an appended iframe's first document already gets the new-document stubs).
- **Heartbeats.** Gate and watchdog each write their heartbeat every 0.5 s; stale after 2 s. Watchdog polls every 0.25 s, holds its own browser-level CDP connection. The gate halts on a stale watchdog after a 5 s start grace.
- **Self-test binding.** `selftest.json` records the browser id from `/json/version`'s `webSocketDebuggerUrl` (new per Chrome launch). `run` refuses when the file is missing, failed, or from another browser id.
- **Live run order** (README "Mirror capture"): `blank --port 9231` → `selftest --port 9231` → `run` + `watch` at nice 10 (`run` refuses while any Fansly target is open: re-run `blank`, which also closes service and shared workers) → wait for `armed: true` → light theme checked → coordinator copies the `/it/pis` reply shape from the local recording into RECIPES (once) → tracer session: `nav /messages` first (baseline observation), the `tracer` plan entries, `nav /messages` again → `stop --port 9231` → `audit --session <id>` → spot-check and Tracer facts into RECIPES → **Phase 3 and 4 code starts here** → later, the remaining entries in as many gate sessions as needed (same pattern, each audited; a failed entry is re-run alone) → `gate.py manifest` → `complete: true` before the coordinator's real generator run.
- **Live prerequisites** (not phase dependencies; each missing one parks the live run for the owner, it never changes the method): the creator Chrome on :9231 signed in; a thread with the fan test account at zero unread; the fan test account's id; the account showing light theme without a write.
- **Identity handling.** Values live only in `identities.json` and the manifest inside the capture folder. Gate, watchdog and audit output name roles and counts, never values, and `gate.jsonl` paths are redacted (Phase 3's "creator username found in <file>" convention starts here). `drive.py` output is not redacted: it prints only to the coordinator's terminal, never to a file in the repo. The fan identity is read only from the creator session: if `--fan-account-id` never appears in an `/account?ids=` reply, the coordinator opens that fan's thread (allowed only at zero unread), and if it still never appears the manifest stays `complete: false` and the gap is parked for the owner.
- **Refresh.** No automation. A new Fansly build is picked up by repeating the live run order from the tracer into a fresh capture root, then the generator (README "Mirror capture").

## Testing Decisions
- **Seam 1, unit tables (plain scripts, house style):** `fansly/test_capture_gate.py` drives `decide` over method × host × path × halted (GET on cdn3 continues; HEAD and OPTIONS continue; POST `https://apiv3.fansly.com/api/v1/message/ack` fakes; PUT to `*.awswaf.com` halts; anything after halt denies), `on_open_reply` shapes and provenance, `redact_path` (`/<username>` and an 18-digit id redacted), `is_stale` edges, `selftest_binds` (missing, failed, other browser id), `unblanked_refusal` (a Fansly page, iframe or service-worker target refused;
