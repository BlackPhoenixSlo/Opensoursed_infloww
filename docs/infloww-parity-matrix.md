# Infloww parity matrix

How close Inflowwww is to Infloww, screen by screen. One row per numbered section of the Inventory (`docs/infloww-screens.md`) except the containers §1, §2, §3 and §6, one row per sub-screen the Inventory tabulates (§3.2's 13 OF Manager items, §3.4's 6 Analytics screens, §3.6's four S4S labels, §3.7's 2, §3.8's 5, §3.9's 3, §3.10's 11 Settings tabs, §4.1's Auto Post and Auto Story), two rows split out of §1.1 and §1.3 so each walked route has a row of its own (`1.1 Help center`, `1.3 Login`; ticket 41, see the Route walk ASSUMPTION below), and three cross-cutting rows, X1, X2 and X3. The rows were seeded from the Baseline table of `docs/plans/infloww-parity-next-steps.md` (Phase 0, spec `docs/spec/phase-00-merge-stale-docs-route-matrix.md`). Later Phases edit rows in place: they change a row's cells, never its `§` id, and never add a second row for the same id. `.scratch/infloww-parity-next-steps/suite.sh` (step `matrix`) checks the contract below.

**Columns, in order.**
- `§`: the Inventory number. A sub-screen row puts the number, a space, then the Inventory label (`3.2 Vault`). Cross-cutting rows are `X1`, `X2` and `X3`.
- Infloww surface: what Infloww shows there, in the Inventory's words.
- Inflowwww route: our route in the Merged tree, or `none`.
- Visual evidence: the Infloww evidence the row is graded against (a C[...] tag of the Inventory, a Clone file `ui-redesign/infloww-exact/<name>.html` (the Clone was deleted in cleanup Phase 2, 2026-10; tag `legacy-ui-final` keeps the cited files), a bundle selector or a help article id `H<id>`), then ours: the Route walk's shots, a committed screenshot or a harness, or why there is none. The Route walk shoots every Clone file a row cites at 1440x900 (`/tmp/route-walk/clone-<name>.png`, never committed).
- Data source: the relay route, store or module the screen reads.
- Read/write: what the screen reads and what it writes, then `(scope: …)`: the relay test file that grades the Permission scope cell (phase-06 spec: graded from the relay tests, never from a shot), or why there is none.
- Permission scope: the principal the relay checks for that surface: `user session`, `chatter session`, `user session + X-Employee-Id`, `public` or `unverified`, with `(account-scoped)` when the route also passes `X-Account-Id` through the account isolation gate (`_account_isolation_middleware`, `service/server.py`). Several principals are comma-separated. `none` means no relay route backs the surface.
- Remaining gap: what still differs from Infloww, with the ticket or Phase that owns it, each difference led by its kind tag: `[layout]`, `[type]`, `[responsive]`, `[labels]`, `[states]` (empty, loading, error, Not wired and Not applied yet states), `[dialogs]`, `[keyboard]` or `[nav]`. Keyboard and loading differences come from the `scripts/ui-shots.sh` flows, the `scripts/settings-check/walk.py` scenarios and the code, never from a still shot. An `unverified` row ends with why no evidence settles it. `none` when nothing is known.
- Matrix status: one of the seven below.
- Inventory version: the Infloww build the row's evidence comes from: `v5.7.14` (the sidebar capture and clone, [BS]/[CL]/[PAL]) or `v5.7.20` (the Dashboard bundle and the help centre), or both.
- Phone: `intentionally improved` for a row that names at least one backticked route in Inflowwww route and whose Matrix status is neither `missing` nor `blocked` (the Route walk shoots that route at 390×844 and fails on sideways scroll); `n/a` for a row with no route, and for a `missing` or `blocked` row (Phase 6 spec, Contracts). A row whose route cell names no backticked app path (one starting with `/`), such as the whole-app rows §1.1, §1.2, §1.4 and §5 (`every route`), reads `n/a`; §5's phone grade is carried by the per-route Phone cells. The Route walk (`/tmp/route-walk-src/walk.py`, never committed) fails on a Phone cell that breaks this rule.

No cell is empty: a cell with nothing to say reads `none`.

**Matrix status** (the glossary's, `CONTEXT.md` "Matrix status"):
- `matched`: our screen does what Infloww's does.
- `intentionally improved`: Inflowwww has something stronger on purpose (its extras, labelled per ADR-0003, and phone layouts).
- `intentionally different`: deliberately not built the Infloww way, because it needs Infloww's global customer base or desktop app.
- `not wired`: we show the surface, but named controls or reads are not backed by the relay (they render disabled or "Read-only in Inflowwww for now" and never fake success).
- `unverified`: no fresh evidence settles the grade; the Remaining gap says why. Phase 6 re-walks every route.
- `missing`: Infloww has it and we do not.
- `blocked`: it cannot be built without something outside this deployment (a live check, an unknown request body, a backend we do not have).

Seeding rule (spec): Baseline done becomes `matched` (`intentionally improved` for an Inflowwww extra); partly becomes `not wired` when the evidence names unbacked controls, else `unverified`; missing stays `missing`; intentionally different stays `intentionally different` (`intentionally improved` for phone layouts); blocked stays `blocked`. The Messages Pro row and the Settings tab rows copy their grades from `docs/messages-pro-parity.md` and `docs/settings-parity.md`; they are not re-graded here.
